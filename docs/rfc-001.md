# RFC-001: Salvage Radio

**Status:** Final
**Author:** Pete (cargopete)
**Created:** 2026-05-15
**Last updated:** 2026-05-16

---

## Summary

Salvage Radio is a terminal-based feed aggregator built on the WebAssembly Component Model (WASIp2). It presents RSS/Atom feeds as **radio stations** rather than inboxes: each station is an independent `.wasm` component with its own editorial logic, and the user *tunes in* to one station at a time through a TUI styled as a piece of recovered industrial equipment.

The project has two reasons to exist:

1. **A different relationship with feeds.** The inbox model (unread counts, list views, mark-all-as-read) creates obligation. The radio model creates ambience. You tune in, listen for a while, tune out. Missing items is normal — radio doesn't replay everything you missed while the set was off.
2. **A real workout for WASIp2.** Stations as components is a genuine use case for the component model's strengths: capability-scoped sandboxing, single-artifact distribution, polyglot-by-default even if the author chooses not to use it. The frontier work — `wasi:http`, resources, eventually streams and async — all gets exercised.

This is a hobby project. It does not need to scale, federate, or replace anything.

---

## Goals

- A single statically-linked host binary that loads station components from a directory and renders them through a TUI.
- A stable, minimal WIT interface that third parties (or future-Pete) can implement to publish a station.
- A capability-sandboxed runtime: each station gets only `wasi:http/outgoing-handler` (scoped where possible to declared domains), `wasi:clocks`, and a small key-value cache. No filesystem, no env, no sockets.
- A TUI with a coherent steampunk/rusted-brass aesthetic — not a costume of gear emoji, but a disciplined visual language.
- An initial set of seven stations covering the author's actual interests, demonstrating that the WIT interface survives heterogeneous use.

## Non-goals

- Web frontend. There may be one eventually, but it is not part of v1.
- Multi-user / sync / cloud anything. Salvage Radio runs locally and stores nothing the user can't see.
- A general-purpose feed reader. List views, unread counts, starring, foldering, mark-as-read — explicitly out of scope. If you want NetNewsWire, use NetNewsWire.
- A plugin marketplace. Stations are `.wasm` files in a directory. Discovery and distribution are deferred.
- Realtime / push. Stations poll. The radio metaphor accommodates this: a station that has nothing new is just *quiet*, which is a normal state for a radio.

---

## Background and prior art

**Feed readers.** The dominant interaction is inbox-style: Feedly, Inoreader, NetNewsWire, Miniflux, FreshRSS. All of them are well-built; none of them are what this is.

**Radio-style information consumption.** Closest precedents are NPR One (algorithmic audio feed), the late lamented "Stations" feature on various podcast apps, and — in spirit — the "river of news" model Dave Winer has championed for two decades. Salvage Radio is essentially a Winer river-of-news with explicit channels and a much weirder aesthetic.

**Component-model applications.** Most public WASIp2 demos are either "hello world in seven languages" or serverless-shaped (Spin, wasmCloud). There is a gap in the ecosystem around *desktop-shaped* component applications. Salvage Radio fills it for a project of one.

```
┌──────────────────────────────────────────────────────────────┐
│  host (native binary, Rust + ratatui + wasmtime)             │
│                                                              │

│  │  TUI layer   │←──│  station        │←──│ wasmtime     │   │
│  │  (ratatui)   │   │  registry &     │   │ component    │   │
│  │              │   │  scheduler      │   │ runtime      │   │
│  └──────────────┘   └─────────────────┘   └───────┬──────┘   │
│                                                   │          │
└───────────────────────────────────────────────────┼──────────┘
                                                    │
                            ┌───────────────────────┼──────────────────┐
                            │                       │                  │
                       ┌────▼─────┐           ┌─────▼────┐       ┌─────▼────┐
                       │ bg-pol   │           │   tech   │  ...  │ pastoral │
                       │  .wasm   │           │  .wasm   │       │  .wasm   │
                       └──────────┘           └──────────┘       └──────────┘
                       (component)            (component)        (component)
```

The host is the only thing that touches the OS. Stations are pure components that receive an `wasi:http` handle from the host and return `signal` values.

### Process model

Single process, single binary. Wasmtime async runtime on tokio. One `Store` per station instance (so a misbehaving station can't corrupt another). Stations are instantiated lazily on first tune-in and kept warm thereafter.

### Threading

The TUI runs on the main thread (crossterm requirement). The wasmtime runtime, the per-station tick loop, and HTTP I/O run on a tokio multi-threaded runtime in the background. Communication between the two halves is via `tokio::sync::mpsc` channels.

## The WIT interface

This is the single most important design surface in the project. It needs to be small enough that writing a station is a weekend, opinionated enough that stations feel coherent across the dial, and flexible enough that "Bulgarian politics aggregator" and "Wodehouse-themed literary station" both fit comfortably.

See `wit/station.wit` for the canonical interface definition.

### Rationale for the design choices

**`signal` as a variant, not an option or a result.** "Nothing new" and "I'm broken" are different states with different UI treatments. A station that's been silent for an hour is fine; a station that's been off-air for an hour gets a visible warning indicator. Modeling these distinctly at the type level forces the host to handle them distinctly.

**`tune()` is poll-based, returns one broadcast at a time.** I considered `tune() -> list<broadcast>` and `tune() -> stream<broadcast>`. The list version is fine but makes pacing awkward — if a station returns 50 items, when does the user see them? The stream version is what I actually want but `wit-bindgen`'s async/stream story is still settling. Poll-one-at-a-time is the v0.1 compromise: the host calls `tune()` on the station's declared cadence, the station can return one fresh item per call, and the host paces presentation. **Migration path to streams is preserved**: when async is mature, we add a `tune-stream() -> stream<broadcast>` to the interface as an optional export, with `tune()` remaining as the fallback.

**Stations own dedup IDs.** The host doesn't try to hash content or guess. The station says "this is item `abc-123`" and the host trusts it. Stations using upstream RSS GUIDs get free correctness; stations doing something exotic (merging, summarizing) take responsibility for stable IDs. This pushes complexity into the right place.

**`declared-hosts` is advisory.** WASIp2's `wasi:http` doesn't yet have a clean way to scope outgoing HTTP per-instance. The host can implement scoping itself by inspecting outgoing requests and rejecting those not in `declared-hosts`. This is enforcement-via-host-logic, not enforcement-via-capabilities, but it's the best we can do in 0.2.3. When `wasi:http` adds proper scoping, we move to that.

**`body` is plain text or simple markdown, never HTML.** This is the single most opinionated choice. RSS bodies are HTML soup. The station's job is to **render down to plain text or markdown** before broadcasting. This is a feature: it forces stations to make editorial decisions about what's worth saying. The TUI never has to parse HTML. The user never sees mangled markup.

**`host-cache` is best-effort.** Stations that need to remember "what's the newest item I've seen" use the cache. The host backs it with a small sqlite or sled DB on disk, but the contract is that the cache can be wiped at any time and the station should still work (just by re-emitting some items that get deduplicated).

### Wasmtime configuration

```rust
let mut config = wasmtime::Config::new();
config
    .async_support(true)
    .wasm_component_model(true)
    .epoch_interruption(true)
    .consume_fuel(true);
```

**Epoch interruption** gives the host a way to kill stations that run away (infinite loop in `tune()`). The scheduler bumps the epoch every 100ms; stations get 50 epoch ticks (5 seconds) per `tune()` call before being interrupted.

**Fuel** is a secondary defense — caps CPU per `tune()` independently of wall-clock. Set generously (a billion units), tuned later if a station starts hitting limits.

**One Store per station instance**, kept around between calls. Linker is built once at startup with all host imports registered.

### Capability sandbox

Each station's `WasiCtxBuilder` is constructed with **only** the imports it needs:

- `wasi:clocks` — yes (read-only, harmless)
- `wasi:http/outgoing-handler` — yes, wrapped by `http_guard` which rejects requests to hosts not in the station's `declared-hosts`
- `wasi:io/streams` — yes (required by `wasi:http`)
- `host-cache` — yes (station-scoped via key prefix)
- `wasi:filesystem` — **no**
- `wasi:sockets` — **no**
- `wasi:cli/environment` — **no**
- `wasi:cli/exit` — **no**
- `wasi:random` — yes (harmless, useful)

## TUI design

### Aesthetic principles

The visual goal: **a piece of recovered industrial equipment that someone has cleaned, kept working, and grown fond of**. Brass, not gold. Oxidation, not damage. Heavy and mechanical, not flashy. Restraint above all.

### Motion budget

Two exceptions to the intentionally static TUI:

1. **Warm-up sequence at startup** (~600ms). Machine warming up.
2. **Signal flicker on new broadcast** (~50ms). One frame copper_bright, then back to copper.

## Roadmap

| Milestone | Scope                                                                       | Acceptance                                                         |
|-----------|-----------------------------------------------------------------------------|--------------------------------------------------------------------|
| **M0**    | WIT compiles. `cargo component` builds the tech station to `.wasm`.         | `wasm-tools component wit tech.wasm` shows expected interface.     |
| **M1**    | Headless host. Loads one station, prints broadcasts to stdout.              | Tech station broadcasts visible on stdout, deduplicated.           |

## Open questions

- **Async in stations.** Deferred to M5+.
- **Streams.** Deferred until WASI 0.3 / Preview 3.
- **Declared-hosts enforcement.** Host-side check in `http_guard` is correct for v1.
- **The pastoral station's curation.** Separate RFC before implementing.
- **Per-station rate limiting.** Lean toward trust + host-side circuit breaker.
- **Mouse support.** No mouse in v1.

## Appendix B: terminology

- **Station** — a `.wasm` component exporting the `station` interface.
- **Broadcast** — one item of content emitted by a station.
- **Tune** — both a verb (user action: switch stations) and a noun (the host's call to `station.tune()`).
- **Dial** — the bottom TUI panel showing frequencies.
- **On-air / static / off-air** — the three states a station can report.
